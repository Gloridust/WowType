# 排序评测

排序（候选顺序）是输入法的核心。这里放仓库里固定的评测集、回归集和基线；CI 的「排序评测」任务每次都用真实词库跑一遍，
回归集必须全过、其余各组不许比基线差。改排序的 PR 照这里在本地跑同一套，提交说明里贴前后对比。

## 一条命令跑全套

```bash
scripts/eval.sh <数据目录>                    # 和 CI 一样：回归集必须全过，其余各组和 baseline.tsv 比
scripts/eval.sh <数据目录> --misses           # 再列出每组没通过的用例（其它参数原样交给 wowtype-eval）
scripts/eval.sh <数据目录> --update-baseline  # 打印和旧基线的对比，再把这次的数字写进 baseline.tsv
```

数据目录是 `scripts/make-data.sh` 的输出（`lexicon.tsv`、`words.lm`、`english.txt`，有 `VERSION`、`SOURCE.txt` 更好），
要和基线用的是同一份（`baseline.tsv` 的「数据」一行：词库包版本、rime-ice 提交）：

```bash
# 照 CI 的做法生成（rime-ice 钉在基线记的提交上；words.lm 本机有就用 WOWTYPE_LM_FILE，不然要下载）
want=$(awk -F'\t' '$1 == "# 数据" { print $3 }' tools/eval/baseline.tsv)
git init -q /tmp/rime-ice && git -C /tmp/rime-ice fetch -q --depth 1 https://github.com/iDvel/rime-ice.git "$want" \
    && git -C /tmp/rime-ice checkout -q FETCH_HEAD
WOWTYPE_LM_FILE=/usr/share/wowtype/words.lm scripts/make-data.sh /tmp/rime-ice /tmp/wowtype-data
scripts/eval.sh /tmp/wowtype-data

# 装着的数据正好是这个版本时也可以直接用（/usr/share/wowtype 不可写，脚本会先复制到临时目录）
scripts/eval.sh /usr/share/wowtype
```

脚本先编一个 release 的 `wowtype-eval`（`--no-default-features`，不用语音的系统库；`WOWTYPE_EVAL_BIN` 可以指定现成的），
全部用例在一台普通机器上跑 20 秒左右。数据目录可写时载入词库会在旁边写 `lexicon.tsv.wcache`。

### 和外壳一致的配置

`wowtype-eval`、`wowtype-show` 默认和 fcitx5 插件、macOS 默认设置下一样配引擎（`core/src/bin/common/preset.rs` 逐项对照）：
候选上限 1000（`kMaxCandidates` / `Engine.maxCandidates`）、词库旁边的 `words.lm` 和 `english.txt`、纠错开、模糊音关（分组是默认那几组，
兜底开）、扩展 B 区生僻字关、全拼、简体，上文只给最后 24 个字节（会话的 `CONTEXT_BYTES`）。不带用户词库、输入习惯、自定义词、
领域模型和神经语言模型（CI 里也没有）；会话在引擎候选之外插的 emoji 推荐、日期时间不算。

**首选会随候选上限变**（上限 10 时 `trunc_exact` 的 top1 是 89.7%，1000 时 95.4%；`yingai` 上限 10 首选「应该」、1000 首选「因该」），
所以评测要和外壳用同样的上限。以前的默认（上限 10、只用命令行给的语言模型和英文词表、上文不截）还能用 `--legacy` 跑。

## 评测集

| 文件 | 条数 | 测什么 | 怎么来的 |
|---|---:|---|---|
| `regress.tsv` | 66 | 已知要对的（打全了的词、儿化、英文、双拼、单字、接着上文打、按错键、热词……），**必须全过** | 手写，每条都用真实词库核实过；来源见文件里的注释 |
| `common.tsv` | 1000 | 常用词：词频前 5000 的词，每个拼音取词频最高的那个 | `make_eval.py --count 1000` |
| `mid.tsv` | 1000 | 中频词：第 3 万到 30 万名 | `make_eval.py --skip 30000 --top 300000` |
| `rare.tsv` | 1000 | 冷门词：第 30 万名以后 | `make_eval.py --skip 300000 --top 1000000` |
| `jianpin.tsv` | 1000 | 简拼：常用词每个音节只打声母 | `make_eval.py --jianpin` |
| `trunc.tsv` | 1000 | 少打最后一个字母、截完不是任何词：期望补全出原词 | `make_eval.py --truncate 1 --exact skip --top 30000` |
| `trunc_exact.tsv` | 1000 | 少打最后一个字母、截完**正好是词频 ≥ 1000 的词**：期望就是这些精确词（补全排后面） | `make_eval.py --truncate 1 --exact only --top 30000` |
| `homophone2.tsv` | 300 | 两个音节的输入，词库里每个同音词都排在第一个单字前（看「通过」） | `make_eval.py --homophones 2 --top 20000 --count 300` |
| `homophone3.tsv` | 200 | 同上，三个音节 | `make_eval.py --homophones 3 --top 20000 --count 200` |
| `daily.tsv` | 138 | 手写的日常整句（`daily_sentences.txt`），一次打完整句 | `make_sentence_eval.py --lexicon`：按词库切词取读音 |
| `context.tsv` | 533 | 同一批句子逐词打，带前面已经上屏的文字 | `make_sentence_eval.py --context`（jieba 分词 + pypinyin） |

- 除了 `regress.tsv`、`context.tsv`，都由 `scripts/make-eval-sets.sh <lexicon.tsv>` 一次重新生成：只用 Python 标准库，
  输出只取决于词库（同频的按词库里的顺序），同一份词库生成的文件逐字节一样；每个文件开头记着参数和词库的 sha256。
  抽样是在按词频排好的列表里等间隔取（不用随机数）。
- 少打一个字母为什么分两组：项目的既定规则是「打全了的拼音正好是一个够常用的词时，它排第一」（docs/ENGINE.md「半成品输入」），
  `zhonggu` 本身是「中古」，期望写「中国」就是把正确的行为算成错。所以截完正好是词频 ≥ 1000 的词的单独成组、期望写那个精确词
  （和 `core/src/lib.rs` 的 `EXACT_PROTECT_MIN_FREQ` 一样）；截完是词、但词频都不到 1000 的两组都不收（哪个排第一都说得过去）。
  这组里有些精确词本身就很怪（`kanda` 的「看打」、`rena` 的「人啊」），没过的多半是补全排了第一，要不要改规则另说，评测只量现在的规则。
- 同音词组：同一串字母还能按别的音节数切的（`xian` 是一个音节，也是「西安」xi an）不收，那时单字也是打全了的精确结果。
  「词库里的每个同音词」包括词频很低的，所以这组的「通过」比 top1 严得多。
- `daily.tsv` 不用 pypinyin：每句按词库切词（词数最少，一样多时词频乘积最大），每个词取它在词库里词频最高的读音。
  和 `context.tsv`（pypinyin 标的）对过：138 句里只有 3 处不一样，都是 pypinyin 标错了（微调、越长、还款），`context.tsv` 里这三条已经手改。
  重新生成 `context.tsv` 时（`make_sentence_eval.py --text daily_sentences.txt --context`，要 jieba 0.42.1、pypinyin）记得再改这三条。

### 外部盲测集

`tools/eval/external/` 放别人写的用例（现在是 chime 的 1010 条整句盲测），`scripts/eval-external.sh <数据目录> --nnlm <nnlm.bin>`
跑一遍报数。CI 不跑、没有基线：只用来量自家评测集看不出的问题，不照着它调，见 [external/README.md](external/README.md)。

### 用例格式

```
输入<TAB>期望[<TAB>上文[<TAB>属性]]
```

- 期望：多个可接受的答案用 `|` 分隔；上文：光标前已经上屏的文字（可空）；`#` 开头是注释。只有两三列的老用例照旧能用。
- 属性（空格或逗号分隔，可选）：`top=N` 期望在前 N 名就算通过（默认 `top=1`）；`at=N` 期望正好在第 N 名；
  `before-single` 期望里的每个词都排在第一个单字候选前面；`sp=方案` 这一条按双拼打（`xiaohe`、`ziranma`……）。
- 每组报 top1 / top3 / top9 和「通过」（按属性判断；没写属性的用例「通过」就是 top1）。

## 基线和门槛

`baseline.tsv` 记着每组的条数（用例、top1、top3、top9、通过）和用的是哪份数据。CI 和 `scripts/eval.sh` 每组和它比：

- `regress` 必须全过；
- 其余各组 top1、「通过」任何一个比基线低超过 **0.5 个百分点**就失败（`wowtype-eval --tolerance` 可以改）。
  小组一条就不止 0.5 个点（`daily` 138 句一句是 0.72 个点，`homophone3` 一条正好 0.5），等于这些组一条都不许掉；
- 比基线高超过 0.5 个点会提示「可以更新基线」，不算失败；用例数、数据版本和基线对不上会提示（照样比）。

当前基线（2026-11-17，`origin/pre-release` fd3eb42 的排序代码，rime-ice 927e1cf + `words.lm` lm-2026.11.09 + english.txt，外壳配置）：

### 改了排序怎么更新基线

1. `scripts/eval.sh <数据目录>` 看哪些组变了；`--misses` 看具体哪些用例变了。
2. 回归集全过、没有一组变差（或者变差的那组说得清为什么值得）以后，`scripts/eval.sh <数据目录> --update-baseline`。
3. 把它打印的对比表（「基线 top1」「差」两列）贴进提交说明，和 `baseline.tsv` 的改动放在同一个提交里。

换了数据（rime-ice 提交、`data/` 下的热词和词频表、`words.lm`）也要重写基线，提交说明里写清是数据变了。
评测集本身改了（重新生成、加了用例）同样要重写基线，前后数字不能直接比。

## 排序不变量

排序评测只量「第一个对不对」，量不出「这种结果永远不许有」（`cehaohou` 只剩两个纠错候选时 top1 统计里只少一条）。
`scripts/invariants.sh <数据目录> [--nnlm nnlm.bin]` 把这里全部用例逐键打一遍，检查硬规则：
打对了的拼音第一个不是纠错出来的、第一个音节的单字一直在、候选不会只剩几个、加了上文或神经语言模型照着打的读法还在……
一条都不许违反（`invariants-allow.tsv` 里写明了理由的除外）。CI 在排序评测后面跑它。规则和来历见
[docs/ENGINE-INVARIANTS.md](../../docs/ENGINE-INVARIANTS.md)。

# 以前的手动评测

下面是建这套固定评测集以前的记录（当时的工具默认候选上限是 10，数字和上面的基线不能直接比）。

## 生成用例

```bash
# Tatoeba 中文句子（CC BY 2.0）：https://downloads.tatoeba.org/exports/per_language/cmn/
python3 tools/make_corpus_eval.py --tatoeba cmn_sentences.tsv.bz2 \
    --split /tmp/train.tsv:3000 /tmp/test.tsv:500

# 或者一行一句的纯文本
python3 tools/make_corpus_eval.py --text sentences.txt --out cases.tsv --count 2000
```

## 跑评测

```bash
# 词库 + 词级 LM（--legacy：以前的默认，候选上限 10）
cargo run --bin wowtype-eval -- --legacy --lexicon lexicon.tsv --eval /tmp/test.tsv \
    --lm words.lm --k 1

# 再加上字级神经语言模型（从本机微信输入法里取，见 tools/install_wetype_nnlm.py）
cargo run --bin wowtype-eval -- --legacy --lexicon lexicon.tsv --eval /tmp/test.tsv \
    --lm words.lm --nnlm nlrgpt2_nnlm.bin --k 1
```

## 基线（本机 macOS，debug 构建，2026-11）

词库：雾凇拼音 + jieba 词频合并（936,662 条），LM：`words.lm`。

| 用例集 | 不开 NNLM | 开 NNLM |
|---|---|---|
| Tatoeba 留出 500 句 | 61.4% | **65.2%** |
| Tatoeba 留出 100 句 | 53.0% | **62.0%** |
| 另一组留出 100 句（与训练不重叠） | 68.0% | **75.0%** |
| 手写日常句 138 句 | 84.8% | **91.3%** |

其他观察：

- `--beam 32/48` 基本不变（61.6%）
- `--lm-weight 0.5~0.7` 在 Tatoeba 上略好，但日常句会掉；默认 1.0 是折中
- 500 句里约 31% 的正确句子连 top50 都进不去：瓶颈是覆盖/切分，不是排序权重

## 三件套基线（2026-11，本机）

在「词频融合 + 自适应 LM 权重 + 领域 LM 混合」都打开时：

| 用例集 | 基线 | 三件套 |
|---|---|---|
| Tatoeba 留出 500 句 | 61.4% | **67.6%** |
| 另一组 1000 句留出 | 60.3% | **65.0%** |
| 手写日常句 138 句 | 84.8% | **87.0%** |

具体配置：

- 词库：雾凇 + jieba 合并 + Tatoeba 训练侧词频融合（权重 0.3）
- LM：`words.lm` + `--domain-lm`（当时叫 `--lm2`；Tatoeba 训练侧训的 0.5MB 小模型，权重 0.4）
- 自适应 LM 权重默认开

再叠加 NNLM 重排（`--nnlm nlrgpt2_nnlm.bin`）：500 句 top1 **69.2%**（比不加 NNLM 的 67.6% 再高 1.6）。

## 失败归因（500 句，三件套）

- top1 67.6%，top50 74.2%，剩 129 句进不了前 50
- 111/129 只差一个同音字；其中 19 句是「他/她」代词（无上下文不可判定）
- 可对齐的 86 句里：她→他 14、他→她 5、莉→丽 3，其余分散（花/话、时/是、甚/什、鱼/与…）
- 语料 ∩ CC-CEDICT 只挖出 32 个台湾用词变体（义大利、帐单、咖哩…），不值得默认加

结论：剩下的主要是同音消歧长尾，靠更强的上下文模型，不是词库覆盖。

### 试过但没用的

- 调高 NNLM 特征权重（head_word_nnlm=2/4）：100 句 65.0% -> 64.0% -> 60.0%，反而更差
- 从语料补 159 个专名/复合词（玛莉、莱拉、鲍伯…）：500 句 top1 不变（67.6% -> 67.6%）
- 按输入长度调 LM 权重（#200），见下一节：长度上没有规律，最好的「按长度分段」也不比一个常数强

## 按输入长度调 LM 权重：负结果（#200，2026-11）

#200 想在 33 个字母以内把 `beam.lm_weight` 乘 0.5。33 个字母几乎盖住所有日常输入，实际上是全局减半；
阈值又是在报告结果的那 500 句上挑的。这里换成「调参集、留出集分开」重做一遍。

做法：`make_corpus_eval.py` 默认种子按顺序切 `--split train.tsv:3000 test.tsv:500 tune.tsv:2000 heldout.tsv:2000`，
只在 tune 上挑参数，heldout、test（#200 自己报数的 500 句）、手写日常句 138 句只用来验。
数据包 2026.11.11-3（雾凇 929,405 词 + `words.lm` + english.txt），release，每个输入取前 10 个候选看 top1。
每句在 `lm_weight` = 0.3 … 1.4 各跑一遍，任何「按长度给权重」的方案都能直接从这张表上算。

全局常数（top1 对的句数 / 总数）：

| lm_weight | tune | heldout | test | 日常句 |
|---|---|---|---|---|
| 0.5 | 1227/2000 | 1209/2000 | 308/500 | 116/138 |
| 0.7 | 1235/2000 | 1224/2000 | 310/500 | 119/138 |
| 0.8 | 1237/2000 | 1218/2000 | 312/500 | 118/138 |
| 1.0（现在） | 1196/2000 | 1194/2000 | 305/500 | 119/138 |
| 1.2 | 1149/2000 | 1134/2000 | 292/500 | 117/138 |

按字母数分段，每段最好的权重（句数 / 该段总数）：

| 字母数 | tune 最好 | heldout 最好 | heldout 上 1.0 |
|---|---|---|---|
| 1–15 | 0.7（216/294） | 0.7（214/287） | 205/287 |
| 16–25 | 0.9（495/757） | 0.7（503/755） | 489/755 |
| 26–35 | 0.8（341/569） | 0.7（329/558） | 324/558 |
| 36–45 | 0.7（142/244） | 1.0（120/253） | 120/253 |
| 46 以上 | 0.6（52/136） | 0.7（60/147） | 56/147 |

各段都在 0.6–0.9 之间来回跳，没有「越短越低」：最长那段反而最低，36–45 在两边一个 0.7 一个 1.0。
在 tune 上拟合的方案拿到别的集上（括号里是比 1.0 多对 / 多错的句数）：

| 方案（只在 tune 上挑） | heldout | test | 日常句 |
|---|---|---|---|
| 常数 0.8 | 1218（+47/−23） | 312（+14/−7） | 118（+2/−3） |
| 分两段：42 个字母以内 0.8，以上 0.5 | 1217（+49/−26） | 309（+15/−11） | 118（+2/−3） |
| 每段各用 tune 上最好的 | 1214（+42/−22） | 311（+14/−8） | 119（+2/−2） |
| #200：33 以内 0.5，36 以上 1.0 | 1211（+69/−52） | 311（+22/−16） | 116（+4/−7） |

结论：按长度分段不比常数好，#200 不合。全局把权重降到 0.7–0.8 在 Tatoeba 上是真的有用
（heldout +47/−23，符号检验 p≈0.006），但日常句持平或少 1 句，而且会影响所有输入，要单独评估
（再加上文、万象词库、简拼这几组）以后再定，不在这里改。

#200 还有个实现问题：`make_candidate` 减句首分时用的是没乘系数的 `lm_weight`，单音节的句首分多减了一半，
单字顺序乱了（`shi` 的「十」掉到第 9，`bu` 的第一个成了「部」）。以后要按输入调权重，整条链路要用同一个值。
（常数权重下没有这个问题：加句首分和减句首分乘的都是 `beam.lm_weight`（ef5def8）。
`single_syllable_ranking_ignores_lm_weight` 钉住了：权重 0.5 / 0.7 / 1.5 下单音节的候选顺序和分数都和 1.0 一样，
改回不乘权重这个测试就挂。）

## 全局 LM 权重在现在的词库上重测：不改，还是 1.0（2026-11-14）

上一节说全局 0.7–0.8 在 Tatoeba 上有用、要单独评估。词库后来默认融了 Tatoeba 语料词频（#205，留出 +2.3 点），
所以在现在的默认词库上从头再测一遍。

做法：

- 词库：同一份 rime-ice（927e1cf）、`words.lm`（lm-2026.11.09）、english.txt，release，`--max 10` 取 top1。
  - 「发布」：`scripts/make-data.sh` 默认构建。它融的 `data/tatoeba-freq.tsv` 是从全部 89248 句 Tatoeba 挖的，
    **包括下面的 tune、heldout、test**，在 Tatoeba 各组上的数字偏乐观，只作参考。
  - 「干净」：同样的融法，但语料换成 Tatoeba 去掉 test、tune、heldout 和日常句之后的 84685 句
    （`WOWTYPE_CORPUS`，和 docs/DATA.md §3.3 的做法一样）。选参数、报 Tatoeba 留出都用它。
- 用例：和上一节同一次切分（`make_corpus_eval.py` 默认种子，`train:3000 test:500 tune:2000 heldout:2000`）。
  只在 tune 上扫权重、取 tune 上最好的；别的组都只跑 1.0 和选出来的那个值，heldout 只跑这一次。
- 「+/−」是逐句比较（1.0 错、新的对 / 1.0 对、新的错），p 是双侧精确符号检验。

- Tatoeba 上的好处还在，比融语料词频之前小一点：tune 上 0.7 比 1.0 多对的句数从 +39（1196→1235，上一节的旧词库）变成 +32（1249→1281），

- 不一致：手写日常句掉 3 句、一句没多对（发布词库和双拼是同样三句：「周末一起去爬山吧」「我们在哪里见面」「我在看一本很有意思的书」；

  领域模型的分也在 `lm_weight` 里，跟着一起被压低）；刚学过的整句在 0.7 下 +4/−8（用户搭配的加分在 `LearnedLm` 里，也乘了这个权重）。
- 简拼、中低频词这几组涨得多，但它们的答案就是「词库里最常用的那个同音词」，降 LM 权重就是更信词频，这个涨幅有一部分是自证，
  不能当成用户打字会变好的证据。

要再试的话，先把用户搭配的加分、领域模型挪出 `lm_weight` 再比，0.8、0.85 也要在日常句、NNLM、领域 LM 上跑，而且日常句不能掉。
上文特征（`context_bigram_score`，排序权重 1.0）没有乘 `lm_weight`：权重是 1.0 时两边一致；试过在 0.7 下也乘上，
和 0.7 不乘比：上下文 533 条 +5/−3、test 后半句 +6/−2、日常句后半句 +2/−0，都在噪声里，默认不改权重就不用动它。
