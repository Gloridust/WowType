# 引擎细节、评测与调参

这里是 WowType 拼音引擎的实现说明和实测数字，原先放在 README 里。
怎么安装、怎么用见 [README](../README.md)；接手开发先看 [HANDOFF.md](HANDOFF.md)。

## 词库从哪来

WeType 自己的词库格式还在解析（见下）。在那之前可以直接用开源词库跑通：

```bash
# 雾凇拼音：https://github.com/iDvel/rime-ice
# 会自动顺着 import_tables 递归合并被引用的词库（rime-ice 的条目都在被引用文件里）
python3 tools/rime2tsv.py rime_ice.dict.yaml > lexicon.tsv
cargo run -p wowtype-core --bin wowtype-demo -- --lexicon lexicon.tsv nihao
```

`scripts/make-data.sh` 还会用 `--extra-chars cn_dicts/41448.dict.yaml` 补雾凇的大字表（雾凇默认没引入）：
只加词库里没有的单字读音，频次记成小于 1 的 0.9 / 0.8 / 0.7（基本区 / 扩展 A / 其余）。
频次小于 1 的单字（`LexEntry::is_rare`）不参与组句、不占前几页，只排在翻页长尾的最后
（`Lexicon::lookup_common` 不返回它们，束搜索和句首词都用它）——一个音节的字都能翻到
（hou 97 个、shi 374 个、yi 824 个），整句和前几页和不补时完全一样。
翻页长尾的顺序：句首词、第一个音节的常用字、换一种切法才对得上的句首词（houxuanci 的「后续」= hou xu | an ci）、生僻字。
整个输入正好对得上的词库词（同音词）不在长尾里：它们全部接在束搜索给出的整词后面、排在句首词和单字前面
（`Engine::append_more_candidates`），见下面「候选组成」。

儿化：`wanr`、`yidianr`、`zher` 末尾的 r 按儿化查。词库里儿化词都写成带 er 音节的（`wan er 玩儿`），
所以带儿化标记的音节会再按「音节 + er」查一遍，只要带「儿」字的词（`MemoryLexicon::lookup_impl`）。

引擎支持**半成品输入**：尾部还没成音节时会自动补全（`nih` → 你好，`zhongg` → 中国），
不会出现"打到一半没有候选"。

支持**模糊音**（默认关闭）：`--fuzzy`（插件里在设置界面打开，或 `WOWTYPE_FUZZY=1`）开启后，
`zidao` → 知道（zh/z）、`sangdian` → 商店（ang/an）。一共 16 组，可以分别开关
（`Engine::set_fuzzy_groups` / `wowtype_engine_set_fuzzy_groups`，位掩码见 `syllable::fuzzy`）：
z=zh、c=ch、s=sh、n=l、f=h、r=l、an=ang、en=eng、in=ing、ian=iang、uan=uang、un=ong，默认开平翘舌和前后鼻音这 8 组；
un=ong 和后加的 an=ai、huang=wang、un=iong（jun=jiong、yun=yong）、eng=ong 默认关（后四组微信输入法也有）。
两个音节算相同：声母最多换一步、韵母最多换一步，另外可以整个音节换一次（huang=wang 只能这么表达）。
所以 `zeng` 开着 z=zh、eng=ong 能出「中」，`wanse` 开着 huang=wang、an=ang 能出「黄色」；
n=l、r=l 都开着 n 也不等于 r，an=ai、an=ang 都开着 ai 也不等于 ang。
模糊索引只建一份：键是「全部分组都打开」时能互相换的那一类音节（`syllable::fuzzy_key`），查到以后再用
`fuzzy_groups_between` 逐个音节检查用到的分组是不是都打开了。每个音节记着类和「位置」（从类的起点换过来经过的分组），
两个音节之间的分组就是位置的异或，查一次表，不用拆声母韵母。改开关不用重建 55 万词的索引。
模糊读音和精确读音一起参与组句、排序，不是精确读音没词才退过去：`zong` 也列出「中」，
`dansi` 首选「但是」而不是「单丝」。每用一处模糊音（一个声母或韵母）代价多 `fuzzy_penalty`（默认 2.5），
差不多常用时精确读音在前。

支持**日期时间**、**计算器**（`core/src/datetime.rs`、`core/src/calc.rs`）：
- `wowtype_datetime_candidates(key, 年, 月, 日, 时, 分, 秒, 星期)`：key 是 `riqi`、`rq`、`shijian`、`sj`、`xingqi`、`date`、`time`
  （不认 `rq`、`sj` 这类简拼）时给出几种写法；当前时间由插件按本地时区传进来。插件把它们插在首选后面，
  选中时原样上屏、不学习。双拼下用首选的拼音判断。
- `wowtype_calc_candidates(算式)`：`+ - * / % ^`、括号、小数；算得出来给「结果」「算式=结果」，没写完只给算式。
  插件里全拼时以 `v` 开头打（`v1+2*3`），`v` 之后的数字、运算符进编辑区，空格或 `=` 上屏结果。
  `v` 后面只有一个数时，候选是人民币大写金额、中文数字和数字本身（`calc::rmb_upper`、`calc::chinese_number`，整数到千亿、金额到分）；算式结果是金额时附上大写。

支持**自动学习**：同一个词选够 3 次（可配置，按 30 天减半的热度算）后自动收进用户词库，之后能直接打出来。
词库已有的词也会被记录，相当于记住用户偏好。

学错了可以**忘掉**：`Engine::forget_word(词)` 删掉用户词库里的这个词、它的选词热度（`history.tsv` 里的
`w` 行，也就是「上次选过的放第一」用的那个）和它在前或在后的搭配。词库里本来就有的词删不掉，只是去掉
学到的加分，回到原来的位置；自定义词不动。会话里打字途中按 `Ctrl+Delete`（还有 `Ctrl+退格`、`Shift+Delete`）
忘掉光标处的候选；候选上点右键选「忘掉这个词」按序号忘（`Session::forget`），菜单只给学过的词（`Engine::can_forget`：
用户词库、选词热度、候选新词、它在前的搭配里有它，每样查一次表，展开面板一屏 36 个都问得起），见 [ABI.md](ABI.md)「输入会话」。整句（几个词拼的）只忘这一整句的记录，
里面的词和词之间的搭配（发给 -> 你）别的句子也用，留着。用户词库删空了也照样存（只剩注释行），
不然旧的 `user.tsv` 留着，重启又回来。忘掉的词连同忘掉的时间也写进 `history.tsv`（`f` 行，记 180 天、最多 2000 个）：
Windows 上每个应用进程各有一个引擎，读别的进程存的 `user.tsv`、`history.tsv` 合并时，在忘掉之前学到的这个词
（热度、搭配、候选新词，用户词库里的也去掉）不会合并回来；忘掉以后又选过的（热度的时间更晚）照常留着。
选了又退格撤销的不算又选过。旧版本读到 `f` 行跳过。

支持**自定义词**：用户在设置界面里加的词存在 `custom.tsv`（`编码<TAB>词[<TAB>频次]`，拼音可以不分音节），
插件经 `wowtype_engine_load_custom_words(engine, path)` 载入，每次载入整体替换上一次的，文件不存在就清空，
不写回用户词库。自定义词全拼和简拼都排第一（加了「字节跳动」后 `zjtd` 第一个就是它）。
编码不是拼音但全是字母的（`mail`）单独存一张表，整个输入正好等于它时放在最前面。
词里的 `\n`、`\t` 在词库里保持转义（词库是一行一条的 TSV），`try_input` 最后才换成真的换行、制表符。

支持 **emoji 和符号**（`core/src/emoji.rs`、`core/src/symbols.rs`）：
- 打字时推荐：`wowtype_emoji_recommend(首选候选)`，整个词或句尾两个字以上的词对上 emoji 就给一个，
  插件插在第三个候选。词表是 `core/src/emoji/zh-extra.tsv`（手工整理的聊天常用词）加上
  `core/src/emoji/cldr.tsv` 里够具体的关键词（一个关键词对应不超过 3 个 emoji；「脸」「手」这种不算）。
- 表情面板：`wowtype_engine_emoji_search(engine, query)`。拼音先经引擎转成前几个中文候选，再按 CLDR 中文关键词找；
  同时按英文关键词前缀、符号名（`juhao` → 。）找。`cldr.tsv` 由 `scripts/make-emoji.py` 从 Unicode CLDR 生成，
  只收 emoji 15.0 及以前的（新的系统字体可能还画不出来）。
ASCII 标点会自动转成中文标点（`,` → ，`?` → ？），数字写法里的符号不换，如 `3.14`、`20:22`、`3,000`、`3~5`（`symbols::punct`；标点样式选半角时一律原样）；顿号、问号这类没有半角形态的数字后面照常换成中文标点（`1\` → `1、`）；`/` 等没收录的原样交给应用。

支持**繁体输出**：`--traditional`（插件在设置界面打开，或 `WOWTYPE_TRADITIONAL=1`），需要简繁映射表
`--s2t core/data/s2t.tsv`。仓库里的表由 `tools/opencc2tsv.py` 从 OpenCC 数据生成（Apache-2.0，
版本写在表头），收了 OpenCC 的字符表和整张词组表（STPhrases）：从左到右词组最长匹配优先，
其余逐字转换，和 OpenCC 自己的切法一样，「头发 -> 頭髮」「干净 -> 乾淨」「皇后 -> 皇后」都能转对。
表约 1 MB，开繁体时才载入（约 10 ms，峰值内存多 9 MB 左右）。

英文/未登录串会把原始输入本身作为候选（保留大小写）：`hello` → `hello`，
纯拼音输入被完整覆盖时不会插入原始串。加载英文词表（`--english`，插件放
`~/.local/share/wowtype/english.txt`）后，认识的英文词会按词表里的写法给出
（`github` → GitHub），并排在纠错出来的中文前面；本身就是合法拼音的（`she`、`fan`）排第 6，
前 5 个留给中文。
词表直接用 rime-ice 的英文词典：

    cat rime-ice/en_dicts/en.dict.yaml rime-ice/en_dicts/en_ext.dict.yaml \
        > ~/.local/share/wowtype/english.txt

支持**双拼**（默认关闭）：自然码、小鹤、微软、搜狗、智能 ABC、紫光、拼音加加 7 种方案，
键位和零声母规则按 rime 的方案文件逐个核对过（每种方案全部音节编码、解码往返一致）。
`demo --scheme xiaohe`（插件在设置界面选，或 `WOWTYPE_SHUANGPIN_SCHEME=xiaohe`）。
双拼先解码成带隔音符的全拼（`vsgo` → `zhong'guo`），再走全拼的整套流程：整句、句首词、分段选词、
语言模型都一样，候选的 `consumed` 再换算回按键个数；末尾单个键当声母（`vsg` → 中国）。
重码（各方案都只有 `lo`：同时是 `lo` 和 `luo`）会展开成多种全拼，常用的读法排前面（编辑区显示 `luo'ji`）。
各读法的束搜索结果先按分数合并，再一起走后面按位置排的步骤（选过的提前、原始串/英文的位置、整句和句首词的穿插、
翻页长尾），句首词和长尾按第一名所在的读法算；不是把后一种读法补在末尾，也不是排完再按分数重排
（`loji` 第一个是「逻辑」，不是 lo 读法硬凑的「咯 | 就」；选过的词照样排第一）。
只有末尾悬空的单声母才做末音节补全；配成对的音节已经打全，不再补成别的音节（`ji` 不补成 `jiu`）。双拼下不做按错键纠正。

双拼的**简拼**（`ShuangpinAbbrev`，默认开，#268）：每个键都是声母时（方案的 zh / ch / sh 键，自然码、小鹤是 `v` `i` `u`，
智能 ABC 是 `a` `e` `v`；辅音键是它自己，`s` 和全拼的简拼一样 s、sh 都算），把每个键当成一个音节的声母，翻成带隔音符的
全拼简拼（`sm` → `s'm`、自然码 `vg` → `zh'g`）再走全拼的简拼。隔音符单独隔出来的 `zh` 只当一个声母，不再拆成 z、h
（`graph.rs` 的 `isolated_digraph`）。按双拼读不通时（`sm` 在各方案里都是 sian），整个按简拼出；同样的键按双拼也读得通、
有词时（小鹤 `zg` = zeng，`ui` = shi），双拼读出来的候选一个不少、先后不变，简拼的词只往后加：词库里够常用的整词
（词频 ≥ 1000），最多 6 个，插在第 5 个后面；超过 4 个键（`nihk` 这种打全了的两个音节）不再试。三个数是按评测定的：
全拼的评测集翻成小鹤、自然码的键（8342 条）top1 / top3 / top9 和关掉时一条不差，jianpin.tsv 翻成双拼简拼 top9 从 0 到 88%。

语言模型支持三种来源：内置一元回退、bigram TSV（`--lm`）、ARPA（`--arpa`）。
WeType 自己的 `lmcnmac.bin` 因为只存哈希、无法导出，见 [docs/DATA.md](DATA.md)。

## 真实数据验证

用 rime-ice 全量词库（8105 字表 + base 词库，**552,087 条**）跑了两组评测：

| 评测 | 用例 | 结果 |
|---|---|---|
| 最高频同音词（rank=1） | 400 | **top1 100%** |
| 第 2 / 3 / 5 / 10 高频同音词 | 300 / 300 / 224 / 64 | **top10 均 100%** |
| 长输入（≤20 字母、≤7 字词） | 200 | **top1 100%** |

解读：

- rank=1 全中，说明频次打分的排序方向是对的
- 更深排名的 top10 全中，说明**束搜索和候选收集没有漏词**（不是靠调权重掩盖了召回不足）
- 束宽从 5 到 40 结果完全一致，说明这些输入上束宽不是瓶颈（默认仍取 20，留给长句）

需要说明的局限：这些用例的「期望答案」是按词频取的，所以只能验证**排序与召回的正确性**，
不能验证「人更想要哪个词」。后者需要人工标注的用例，评测工具已支持（见下）。

## 调排序

排序权重不能靠感觉调。仓库带一个离线评测工具：

```bash
# 用例格式：输入<TAB>期望（多个可接受答案用 | 分隔）
cargo run --release -p wowtype-core --bin wowtype-eval -- \
    --lexicon rime.tsv --eval cases.tsv \
    --weights coverage_score=1.5,prob=0,history_count=0.3
```

默认配置和两个外壳默认设置下一样（候选上限 1000、词库旁边的 `words.lm` 和 `english.txt`、纠错开、模糊音关，
逐项见 `core/src/bin/common/preset.rs`）；首选会随候选上限变，所以别拿上限 10 的数字和输入法里比。
仓库里固定的评测集、回归集、基线和 CI 门槛见 [tools/eval/README.md](../tools/eval/README.md)，
一条命令跑全套：`scripts/eval.sh <数据目录>`。

常用参数：

| 参数 | 作用 |
|---|---|
| `--data dir` | 数据目录（`lexicon.tsv`、`words.lm`、`english.txt`） |
| `--k n` | 报告 top-n 召回（默认 3；另外总报 top1/3/9） |
| `--max n` | 候选数量上限（默认 1000，和外壳一样） |
| `--legacy` | 以前的默认：上限 10、只用命令行给的语言模型和英文词表 |
| `--fuzzy` / `--shuangpin [--scheme 方案]` | 用对应模式评测 |
| `--lm` / `--arpa` / `--no-lm` | 指定（或不用）语言模型 |

用例可以从词库自动生成，也可以自己标注：

```bash
python3 tools/make_eval.py rime.tsv --count 300                 # 每拼音取最高频词
python3 tools/make_eval.py rime.tsv --rank 2                    # 取第 2 高频（测候选广度）
python3 tools/make_eval.py rime.tsv --truncate 1                # 截掉末尾 1 字母（测补全）
python3 tools/make_eval.py rime.tsv --jianpin                   # 换成简拼
```

### 语言模型与上下文

`--lm` 吃「prev<TAB>cur<TAB>count」的 bigram TSV，`--arpa` 吃标准 ARPA。
上下文取光标前文本的**最后一个词或最后一个字**去查二元组（中文通常没有空格，
只取「最后一个词」会把整段当成一个词，永远查不到）。

实测上下文消歧：

```bash
wowtype-demo --lexicon lex.tsv --lm lm.tsv xian              # 1. 先
wowtype-demo --lexicon lex.tsv --lm lm.tsv --context 我 xian  # 1. 西安
```

`tools/make_bigram.py` 能从词库反推字二元（`事->情` 这类词内搭配），但它**不能替代真实语料**：
在没有语料的情况下实测，rank1 从 100% 掉到 99%，rank2 的 top10 从 100% 掉到 98.7%——
用它换来的是上下文能力，用频率忠实度做代价。真实语料训练的 LM 才有正收益。

另外，词表里没有的词（例如字级模型评多字词）一律当「无信息」处理，
否则会被按近零概率惩罚，把正确的长词压下去。

### 默认权重的取舍

排序总分是 `path.score + rank_score`。因此 `rank_score` 里**不能**再放已经计入
`path.score` 的特征，否则就是重复计权：

| 特征 | 权重 | 原因 |
|---|---|---|
| `prob` | 0 | 是 `path.score` 的单调变换 |
| `lm_score_with_previous_txt` | 0 | 已计入 `path.score` |
| `context_bigram_score` | 2.0 | 上下文带来的新信息 |

这样上下文才有机会真正影响结果。例子（词库里「先」远高于「西安」）：

```bash
wowtype-demo --lexicon lex.tsv --lm lm.tsv xian            # 1. 先
wowtype-demo --lexicon lex.tsv --lm lm.tsv --context 我 xian  # 1. 西安
```

改完后在真实词库上回归验证：rank1 top1 100%、rank2/3 的 top10 100%、长输入 top1 100%，均无下降。

### 训练权重

有一批「输入 → 我实际想要的词」的标注后，可以直接拟合权重（softmax 交叉熵 + L2）：

```bash
cargo run --release -p wowtype-core --bin wowtype-train -- \
    --lexicon rime.tsv --cases cases.tsv --epochs 300 --out weights.txt
```

输出可以直接喂给 `wowtype-eval --weights`。

实测结论要说清楚：
- **特征能区分的场景**（例如「先」vs「西安」，分词特征 `kind` 不同）训练有效，0% → 100%
- **同音词之间**（特征几乎完全相同）训练无效，0% → 0%——这类需要上下文/LM 特征，
  词库自带的信息不足以区分

输出形如 `用例 200  top1 176 (88.0%)  top3 195 (97.5%)`，并列出没进前三的用例。

还有两个辅助工具：

- `wowtype-probe`：逐键输入探针，从第 2 个字母开始逐位截断，看目标词在每一步是否还在候选里。
  它靠「出现过又消失」这个信号抓到了补全的 bug（见下）。
- `wowtype-bench`：真实词库下的载入耗时与逐键延迟。
配合 `--fuzzy` / `--shuangpin` / `--arpa` 可以对比不同配置。仓库里的
`core/data/eval_sample.tsv` 只是演示用的 13 条。

## 半成品输入

即使输入能完整解析（`zhonggu` 就是 zhong+gu），引擎也会把延伸候选（中国）一并给出——
否则用户打到一半时几乎选不对词。延伸候选按「多打的字母数」扣分（每字母 1.2 nats）。

**但打全了的拼音正好是一个实在的词时，它一定排第一。** 补全的分数里带着词频，高频词补出来
可能比用户打全了的低频词还高：以前 `zhongdi` 出「重点」（zhong dian）而不是「种地」，
`ka` 出「看」，`beiji` 出「北京」。用户按空格上屏的是第一个——打到一半时补全排第二只是
多按一个键，打全了却被换成别的词就是打错字。所以现在：

- 精确全拼、整个输入是一个词（或最后一个词至少两个字）、词频不低于 1000 → 排第一，
  补全和纠错候选排到它后面（通常是第二）；
- 整个输入是一个词时，单字拼凑的（`shidan` 拆成「是 | 但」）也排到它后面；
- 最后是个单字的精确结果（`zhonggu` 拆成「中 | 骨」）不算，补全照常可以排第一；
- 整词盖住全部输入的（`congshanruli` 从善如流）不会被拼凑结果（从善 | 入理）压下去。
- 输入正好是一个完整音节（`xian`、`ji`）时，本音节的字排在补全出来的字（想、就）前面。
  本音节的字很少、补全出来的字很多时（`lia` 只有「俩」，lian、liang、liao 的字几百个；`dia` 的「嗲」），
  束搜索这一段的名额会被补全的字占满，本音节的字一个也留不下（「俩」以前排第 60 个）。
  这时只按这个音节再搜一遍，把不是生僻字的补到最前面（#172）。

为什么「截断 1 个字母」的 top1 掉了是对的：这组用例把 `zhonggu` 的期望答案定为「中国」，
可 `zhonggu` 本身就是「中古」。94 例里截断后的字母恰好是另一个词，这些现在一律给精确词，
补全排第二（top3 从 91.5% 升到 93.6%）；截断后不是词的 206 例 top1 99.5%。详见
[docs/UX-AUDIT.md](UX-AUDIT.md)。

## 按错键与长句

音节图里除了正常音节，还加了四种「纠错边」：按成相邻键（`zhonggup`）、两个键按反（`zhognguo`）、
多按一个键（`nihaoo`）、漏按一个键（`zhongguo` 打成 `zhonguo`）；跨音节的按反（`nihoa`）也算。
每条纠错边扣固定分，路径上纠错次数作为排序特征 `typo_count`。

**打对了的输入不纠错**，这一条不靠分数，是硬规则（`cehaohou` 曾经只出「的好后」「得好后」两个候选：
d 在 c 上面，「的」「得」的词频、神经语言模型给的分比固定的纠错罚分高得多）：

- 「照着打的字母读」的读法：每个词词库里都有，只打了声母、补全出来的音节只在最后一个词里
  （`typed_reading_typos`）。纠错多的候选不排到纠错少的这种读法前面（`typed_reading_first`）：
  `cehao` 先出「测好」，「得好」在第二；`cehaohoi` 纠一处的「测好后」在纠两处的「的好后」前面。
  只和音节数不比它多的读法比：`jintiam` 照字母读要四个音节（jin ti a m），纠一处的「今天」
  两个音节就读完了，照常排第一；`shijain`、`zhrge` 没有照着读的读法，也不受影响。
- 束搜索剪枝时，末词相同但纠错处数不同的状态不并成一条，每个位置上纠错最少的状态至少留 4 个
  （`beam.rs` 的 `prune`）。以前「的 | 好」和「测 | 好」末词都是「好」，只留分数高的那条，
  没纠错的读法走不到底，后面的排序规则没东西可排，`ce` 的单字（句首词按第一名的音节边界对齐）也跟着没了。
- 神经语言模型的分数以纠错最少的读法里最顺的那条为基准，比它还顺的纠错路径不加分（`nnlm_scores`）。
  以前拿「的好」当基准，「测好」这些没纠错的整句全被扣十几分，输给没让模型打分的生僻词。

- 后面按位置挪候选的步骤（`protect_exact_input` 把补全的整句挪到精确的整句后面……）不能把纠错的又挪回第一：
  `protect_exact_input` 之后按位置再拦一次（`typos_after_typed`）。`sheihaiyo` 曾经出「谁还要」（yo 当成漏按的 yao），
  因为前面压它用的基准是补全出来的「谁还有」，补全的被挪走以后它又成了第一。
- 第一名是纠错出来的时，句首词也按照着打的读法的音节边界对齐（`prefix_on_syllable_boundaries`）：
  `yusezhi` 的第一名「越职」（yue zhi）一个边界都对不上字母，以前句首词和 yu 的单字全被筛掉，整个候选框只有 6 个。

- 模糊音关着时兜底补进来的词（`fuzzy_fallback`：`shengme` → 什么）带标记 `Feature::fuzzy`（不是排序特征）。照着打的读法本身是词库里的常用词时
  它排在那个词后面（`fuzzy_after_exact_word`：`penyou` 出「喷油」「朋友」），只能硬凑时才排第一。
  它排第一时不当「打全了的整词」，`compose_candidates` 不拿它去筛硬凑的整句：接着上文打 `ninke` 时补进来的「宁可」
  曾经把照着打的「您可」整个筛掉。

没有零纠错的读法能把输入读完时，纠错结果照常排到前面。

**纠错候选有名额**（`settle_corrections`，整条管线的最后一步）：排第一的不是纠错出来的时，纠错的候选只留最前面的 3 个
（`TYPO_QUOTA`）在原来的位置，其余挪到整个列表的最后。以前 `nishi` 的第 12 到 36 个全是纠错出来的「即使、笔试、迷失……」，
把 ni 剩下的单字压到第五页以后。排第一的本身是纠错的（`zhognguo`、`jintiam`）时不限。见 ENGINE-INVARIANTS.md 第 6 节。

这些规则有没有被哪个改动冲掉，由排序不变量检查（`scripts/invariants.sh`，CI 里每次都跑）逐键查，
规则、和 librime / libime / libpinyin 的对照见 [ENGINE-INVARIANTS.md](ENGINE-INVARIANTS.md)。

长句改成**逐位置束搜索**：每个位置只留分数最高的若干条路径，一整句不用枚举全部切分。
剪枝时同一个末词最多留 3 条历史（`BeamConfig::histories_per_word`，前面的字得不一样）：只留一条就是二元模型下的维特比，
选得出分数最高的整句，但最后剩下的几条整句只在句尾不同，句子中间的另一种写法（海边的「完风 / 晚风」吹着真凉爽）早被并掉，
整句增强模型重排时看不到。留 3 条以后，别人写的整句（`tools/eval/external/` 的 1010 条盲测，带模型）top1 59.5% → 63.6%，
前 9 个里有正确整句的 64.8% → 72.6%；自家各组不带模型时逐条不变，带模型时 `daily` 少一条；逐键延迟平均 3.0 → 3.05 ms。
这个思路来自 chime 的 prefix-diverse beam（只借思路）。
束搜索的整句之外，
同时会给出「句首词」候选（`nihaozhongguo` 里的「你好」），选了它就只上屏这一段、剩下的拼音继续打。
句首词只在音节边界上切（单音节 `dan` 不会出「大」），4 个音节以上的输入里第二位放整句开头
最长的那段（我今天晚上要加班 → 我今天晚上），短输入里最多 3 个、放在最后，总数不超过候选上限。

实测（rime-ice 55 万词库 + 英文词表，`wowtype-eval`，各组几百例）：

| 场景 | 改前 top1 / top3 | 改后 top1 / top3 |
|---|---|---|
| 完整输入，常用词（前 5000） | 100 / 100% | 100 / 100% |
| 完整输入，中低频词（3 万–30 万名） | 95.5 / 99.8% | **99.0 / 100%** |
| 按成相邻键 | 0 / 0% | 85.7 / 90.1% |
| 两键按反 | 0 / 0% | 93.0 / 96.5% |
| 多按一个键 | 0 / 0% | 95.9 / 97.7% |
| 漏按一个键 | 14.0 / 16.9% | 33.2 / 44.0% |
| 长句（整句） | 16 / 20% | 72 / 80% |
| 长句 + 一处按反 | 0 / 0% | 60 / 68% |
| 日常句子（80 句） | 5.0 / 6.2% | 85.0 / 90.0% |
| 截断 1 个字母，截完不是词 | 100 / 100% | 99.5 / 100% |
| 截断 1 个字母，截完正好是另一个词 | 75.5 / 91.5% | 12.8 / 93.6%（有意为之，见上一节） |
| 截断 1 个字母，中低频词 | 89.8 / 97.5% | 89.0 / 97.0% |
| 简拼 | 94.3 / 94.3% | 94.3 / 94.3% |

「改前」是 main 分支。每组几百例，用 `wowtype-eval` 跑，中低频那组用
`tools/make_eval.py --skip 30000 --top 300000` 生成——只测前 5000 个常用词时
「zhongdi 出重点」这类问题根本看不出来。

漏按最难：少一个字母时可能正好是另一个合法拼音，很多时候没法判断。
逐键延迟 p99 约 10–13 ms（全量词库，含纠错和句首词；当时的测量，条件见下面[性能](#性能)一节的逐键表）。纠错可以在设置界面关掉（或 `WOWTYPE_TYPO=0`）。

简拼的质量单测：`--jianpin` 生成只取首字母的用例，300 例 **top1 95.3%**。

逐键输入用 `wowtype-probe` 检查：从第 2 个字母开始逐位截断，统计目标词是否还在候选里。
它抓过一个真 bug——补全把未完成的尾巴当成了合法前缀（`shesh` 被当成能解析的 head），
导致 `设施` 从来没被补出来。修好后「出现过又消失」的用例为 **0**。

简拼的「半成品」（`jz` 想打 `jzm` 江泽民）**不做前缀补全**：`jz` 本身可能就是要打
「记者/戒指」，按词频给精确结果符合主流输入法行为；实测加前缀补全后，10 个候选位
会被同分数的短词占满，长词仍进不了前 10，收益为零而复杂度上升。

## 全拼混简拼（省略韵母）

有的音节打全、有的只打声母：`kyi` → 可以（k + yi），`yongzwen` → 用中文（yong + z + wen）。
音节图的 `GraphMode::Mixed` 每个音节都可以走全拼边或声母边，引擎在全拼走不通时用它：

- 全拼（不靠纠错和补全）能走完：只用全拼，和以前一样；
- 输入全是声母（`zg`、`jzm`）：纯简拼，和以前一样；
- 全拼加补全已经能走完（打到一半的 `yanzhon`）：不用混合图——补全按缺几个字母扣分更准，
  混合图在长句上路径多得多，逐键会从几毫秒涨到几十毫秒；
- 其余（`kyi`、`yongzwen`、`hello`）：混合图和全拼纠错/补全的结果按分数合并。

每个省略的音节扣 2.0（自然对数），输入最后一个字母当省略的声母再扣 4.0
（`huiyint` 的 t 多半是多按的，不是「他」）；拿声母和单个字母兜底凑出来的候选直接丢掉
（`h e l l o` 拼成的 "hello" 不能挤掉英文原词）。词库按声母索引查混合查询，再逐个比对打全的音节；
`has_longer` 按声母前缀剪枝。

| 测试集（雾凇 89 万词） | 改前 top1 / top3 | 改后 top1 / top3 |
|---|---|---|
| 全拼混简拼（500 例，2–4 字词随机省略一部分韵母） | 17.6 / 27.0% | **60.6 / 83.6%** |
| 按成相邻键（500 例） | 63.6 / 75.4% | 58.8 / 75.0% |
| 简拼（500 例） | 94.2 / 94.2% | 94.4 / 94.4% |
| 截断（400 例） | 89.0 / 97.5% | 89.0 / 97.5% |
| 整句 / 常用词 / 中低频 | 不变 | 不变 |

按错键掉的几个点是两种读法本来就都成立的输入：`jifk` 按混简拼是「积分卡」（ji f k），
按错键是「肌肤」；纠错结果基本还在前三（top3 不变）。逐键延迟和改前持平（整句 p99 约 6 ms）。

### zh / ch / sh 当一个声母

简拼里 `zh`、`ch`、`sh` 可以当一个声母：`zhch` → 支持，和全拼混着也行，`zhchi` → 支持、`shjie` → 世界。
音节图在相邻的 `zh`/`ch`/`sh` 上多加一条两个字母的声母边（隔音符隔开的 `z'h` 不加），
`z`、`h` 分开的那条路照样保留。查询里用大写的 `Z`/`C`/`S` 和单字母的 `z`/`c`/`s` 区分：
`z` 匹配 z 和 zh 开头的音节（`zg` → 中国照旧），`Z` 只匹配 zh 开头的。词库仍按首字母查，
再逐个核对声母。

代价是两种读法都成立的输入现在偏向 zh：`shs` 第一个从「上海市」（s h s）变成「事实」，
`ch` 从「策划」变成「成」。简拼测试集（只取首字母生成）top1 94.2% → 93.2%，掉的 5 例都是这种；
其它测试集不变。

## 候选怎么排、怎么学（照微信输入法 3.0）

对照的是 WeType macOS 3.0.0 引擎里的符号（`RemoveDupSentenceProcessor`、`GenerateWordsAndRunes`、
`FirstUserCandidateRankerProcessor`、`SingleUserWordCanbeSecond`、`history_hot_val`、
`context_bigram_score`），只借思路，不用它的词库和模型。

**候选横排**（设置界面里可改竖排，或 `WOWTYPE_VERTICAL=1`）。横排时左右键移动、上键翻页，下键展开成 6 列的候选面板（照微信输入法；fcitx5 的候选框只能画一行或一列，所以面板是竖排列表、每项一行 6 个词，用全角字符对齐，光标处的词用〔〕框起来）。

**候选组成**：整句只留几个，后面是词，再后面是单字——

- 整句（几个词拼的）最多 1 个（2 个音节以内）、2 个（3 个音节）、3 个（4 个以上）；
  只差最后一个字的整句（横向候选词 / 横向候选此）只留一个。
- 整个输入正好是一个词的同音词（是的、似的、使得）不算整句，照常排，而且**全部**排在句首候选和单字前面：
  束搜索只留分数最高的十来条，名额常被纠错、补全出来的高频词占掉，剩下的同音词（tongde 的「通的」、
  dachuang 的「大创」）从词库直接查出来补在后面。两个音节的同音词最多 32 个，按使用频率算 90% 的输入不超过 8 个。
- 三个音节以上、整个输入正好是词库里的一个词时（qidongqi 启动器、qianhouduan 前后端），这个词排在几个词
  拼出来的整句（启动 | 其）前面，不看词频（rime-ice 里这类词多半只有占位的词频）；用户选过的整句不动。
- 再往后是句首候选：整句去掉最后一个词（横向候选词 -> 横向…；我今天晚上要加班 -> 我今天晚上要），
  然后是从输入开头起的词，长的在前，最后最多 6 个单字。

**学用户的习惯**（存在 `~/.local/share/wowtype/history.tsv`，和用户词库放一起，重启不丢）：

- 热度：每选一次加 1，30 天减半（不取整，存盘带小数）。排序用 ln(1+热度)。
  以前的历史特征按「距今秒数」扣分，一小时前选过的词反而排在没选过的后面，已经去掉。
  衰减到 1/32 以下的记录（选过一次的约 150 天）存盘时丢掉。
- 同一串输入上次选过的候选：词和整句放第一；单字的第一个候选不动（偶尔选一次生僻字不该一直顶掉常用字），
  选过的字按热度从第二位起排，最多 3 个（找过的字下次就在第一页，几次手滑也不会把常用字挤到第二页；#161）。
  两样都有时（xian 选过「西安」也选过「先」）词照样放第一。
  热度衰减到半次以下（选过一次的 30 天以后）就不再提前：误选一次的词不会长期排第一。
- 自动收词看衰减后的热度：几个月里零零散散选过三次的不算「选够 3 次」。
- 分几次选出来拼成的词（四个字以内）：第一次只记成「候选新词」（history.tsv 的 `n` 行），
  30 天里第二次这样拼出来、或者直接选了它，才收进用户词库。以前用一次就收，挑错一个字拼出来的
  （「你好事竣」）也成了用户词。
- 英文原串（词表里没有的人名，如 `Verah`）：**回车上屏的原始字母串照样不学**（终端里的密码会明文留下）；
  用户从候选框里主动选了纯字母、2~32 字节的串，才记一次热度（`history.tsv` 的 `e` 行），选够 3 次收进
  用户英文词表。以后打 `verah` 还原成 `Verah` 并排第一（完整拼音的 `long`、`she` 除外），
  `Ctrl+Delete`、右键「忘掉这个词」能忘掉。输入带显式大写、而中文只能靠纠错或未登录单字凑出来时，原始串也直接排第一
  （`Verah` 不会被 `ve'ra'h` 拼成的「个大和」挤到后面）。
- 撤销：选了句首词又按退格把它退回编辑区、按 Esc 放弃（失去焦点也算）时，选它时学到的（热度、搭配、
  因此收进用户词库的词、候选新词）退回去；上屏后紧接着按退格（编辑区空着，退格交给应用删字）也退回
  刚才那次上屏学到的，只退最近一次、只在上屏后没按过别的键时。引擎记着最近的学习改动
  （`Engine::learn_mark`、`Engine::undo_learning`，改之前的值都记下了，不用重算），只改回后来没再被改过的。
- 词搭配：上屏时记下「上一个词 -> 这个词」，包括一段一段选出来的整句（我们 -> 再 -> 讨论），
  以及上一次上屏的最后一个词 -> 这次的第一个词。束搜索给学过的搭配加分（用过一次约 +1.7）。

**联想**（设置里的 `Association`，默认关）：选词上屏、整句上屏以后，按上文末尾的词（最近一次选的词，
没有就试末尾 4、3、2、1 个字）查 `Engine::predict_next`——先是学到的搭配（这个词后面选过的，热的在前），
再是词级模型（`words.lm`）里常跟在后面的词——去掉标点、单个字母、和刚上屏的一样的，给一页放进候选框
（`Engine::associate`）。联想出来以后接着打字、数字、标点、空格、回车都照常（数字不选联想）；按 Tab 进联想行
再用空格、回车、数字选，选中的和普通选词一样学，接着出下一轮。键位见 [ABI.md](ABI.md)「输入会话」。
有整句增强模型时（现在随安装包自带）候选按它重排：词级模型给的是 ln(P(词|前词) / P(词))，按它排偏向罕见的
固定搭配（你好 -> 久放），所以取前一个词的全部后续词，按字级模型给「下一个字是这个词的第一个字」的概率
留 12 个，再算整词的概率（按字数平方根折算）排一页；首字概率低于 1/400 的不要，学到的搭配照旧在最前。

**排序参数**：束搜索的语言模型权重 0.85、纠错代价 8.0、补全代价 1.2 -> 1.5，排序特征里上文搭配 1.5、
整句增强模型 1.5，是 `tools/tune_weights.py` 在固定评测集（`tools/eval/`）上自动调出来的：每组用例按奇偶行分成
调参、检验两半，只在调参的那一半上坐标搜索，回归集必须全过；检验那一半平均 91.06% -> 91.65%。完整评测集上
（带整句增强模型）：常用 96.3% -> 96.7%、中频 92.9% -> 93.8%、冷门 87.8% -> 88.8%、简拼 59.5% -> 63.0%、
截断 90.8% -> 92.2%、截断精确词 95.4% -> 96.7%、上文 94.0% -> 94.7%，日常整句持平；不带模型时上文 -0.7，其余都涨。
改参数前先跑它；不用任何用户的输入记录。

**整句增强模型**（字级神经语言模型，`core/src/nnlm.rs`）：给束搜索的前 8 条整句重排（特征 `head_word_nnlm`，
权重见上面「排序参数」）。默认用 WowType 自己训的 `nnlm.bin`（3 层 GPT-2，宽 256，字表约 7000 字，LCCC + 中文维基，
`tools/nnlm/`），用户也可以导入微信输入法自带的那个（两者效果相近）。没有上文时，输入至少 5 个音节才用它：
单独一个词（kexue、jieran）时它只会比较「哪串字常见」，会盖过词库对整词的判断（`NNLM_MIN_SYLLABLES`）。
`scripts/eval.sh` 实测：门槛 0、权重 1.0 时日常整句 +2.2、上文 +5.1，但常用词 -3.5、简拼 -6.7、截断 -8.7；
现在的设置下单独打词的各组和不带模型时一样，日常整句 90.6% -> 94.2%，上文 89.1% -> 94.0%，逐键平均多 0.7 ms。

开销有两道限制（#227）：第一条整句一半以上的音节是只打了声母、纠错出来或词库不认识的长输入
（`sdsjdsdsd`、`asdfghjkl` 这类乱按）不重排——硬凑出来的整句挑哪串更顺没有意义，以前每键要多算几十个字，
乱按一串平均每键从 3 ms 涨到 7–10 ms；一次重排最多算 64 个字（几条整句按公共前缀合并后数，`NNLM_MAX_CHARS`），
日常整句逐键打一次最多 59 个、平均 20 个，碰不到这个上限，评测和不限时一样。

`wowtype-eval --learn` 先把每个用例按插件里的选法「打一遍、上屏正确答案」再测，
`--learn-from <文件>` 用另一组用例学，看学了一组会不会把别的组带坏。40 句日常句子：

| | 不学 | 学一遍以后 |
|---|---|---|
| 日常句子 | 90.0% | 95.0% |
| 中低频完整输入 | 99.0% | 100% |
| 截断 1 个字母 | 89.0 / 97.5% | 92.8 / 98.8% |
| 学了句子以后的常用词 / 中低频词 | 100 / 99.0% | 不变 |

还差的是真正的语言模型：没用过的搭配（祝你/祝您、在/再）只能靠词频，要用语料训练词级 bigram 才能解决。

`wowtype-show --lexicon lexicon.tsv --english english.txt 拼音...` 按插件的配置打印候选，
每个候选标出是整句、词、句首候选还是原始串。

## 性能

逐键延迟（`wowtype-bench --typing`，#43 的 4 条用例共 50 次按键；i5-13490F、Linux、release、rime-ice 891,526 词，2026-11）：

| `--max`（候选上限，输入法里是 300） | words.lm | 均值 | p95 | p99 |
|---|---|---|---|---|
| 18 | 不带 | 2.70 ms | 6.08 ms | 6.11 ms |
| 300 | 不带 | 2.81 ms | 5.91 ms | 6.34 ms |
| 18 | 带 | 2.95 ms | 6.37 ms | 7.21 ms |
| 300 | 带 | 3.36 ms | 7.30 ms | 7.53 ms |

同样的用例在 Apple M3（macOS，release，pre-release 分支，雾凇 929,380 词，2026-11-13）上重测。两个外壳现在的上限是 1000：

| `--max` | words.lm | 均值 | p95 | p99 | 最慢 |
|---|---|---|---|---|---|
| 18 | 不带 | 1.9–2.4 ms | 3.8–4.4 ms | 4.3–4.5 ms | 9 ms（第一个键，冷启动） |
| 300 | 不带 | 2.09 ms | 4.22 ms | 4.53 ms | 5.00 ms |
| 1000 | 不带 | 2.1–2.2 ms | 4.4–4.7 ms | 4.8–5.1 ms | 5.41 ms |
| 18 | 带 | 2.07 ms | 4.46 ms | 4.83 ms | 5.24 ms |
| 300 | 带 | 2.28 ms | 4.81 ms | 5.20 ms | 5.62 ms |
| 1000 | 带 | 2.58 ms | 5.43 ms | 5.96 ms | 6.06 ms |

最慢的都是 20 个字母的长句（xiangquzijieshangban）。上限从 18 加到 1000，p95 只多 1 ms 左右。
#43 在 M2 上测到的「300 比 18 慢两倍多、长句单键 25–45 ms」在这里看不到，所以先不做「先算一页、翻页再补」。
上面都是模糊音关着（只有兜底）；开着测加 `--fuzzy 0x7C7`（默认的 8 组）或 `--fuzzy 0xFFFF`（全部 16 组）。

**乱按的长串和大词库（#227）**。万象 173 万词下乱按（`sdsjdsdsdsdsj`、`asdfghjkl`）以前每键 7–20 ms。
剖析下来时间在：简拼 `s`、`sd` 一次能查出上万个词，每个都复制一遍词条（三次内存分配）、每个都拿两把读锁算代价、
造一个带两个 String 的候选再整组排序，只留前 32 个（`collect_spans`）；翻页长尾每组留上千个时去重是平方的；
建纠错图时每个位置试几百种拼法，每种走一遍字符串二分（`Syllable::from_text`）；神经语言模型一步一步算，
每步把十几 MB 权重从内存读一遍。改法（候选一个不变，逐键前 50 个候选改前改后逐字节比过）：
`Lexicon::visit` 不复制地逐条给词、代价的总频次一次取好；组内只排下标、先挑出前面一段排好，不够再排剩下的；
留得多时去重查哈希表；音节查预先算好的表；同一层要算的几步前向放在一起算（每行权重读一次给几句用，
`Nnlm::score_many`），x86-64 上按 AVX 编译、几行点积交错着算。和以前一位不差：同样的乘加、同样的先后，没有 FMA。

`wowtype-bench --nnlm nnlm.bin --max 1000 --typing`，i5-13490F 绑在大核上（`taskset -c 4`），2026-11：

| 词库 | 用例 | 改前 均值 / p99 / 最慢 | 改后 均值 / p99 / 最慢 |
|---|---|---|---|
| 万象 173 万 | 乱按 5 条（69 键） | 7.5 / 21 / 22.5 ms | 2.7 / 7.5–8.4 / 12.4–12.9 ms |
| 万象 173 万 | 日常整句（3114 键） | 7.6 / 20 / 36 ms | 3.6 / 10.1–10.3 / 18.5–19.1 ms |
| 雾凇 93 万 | 乱按 5 条 | 3.9 / 9.4–9.8 / 10 ms | 1.9 / 5.4–6.0 / 5.6–6.4 ms |
| 雾凇 93 万 | 日常整句 | 4.8 / 15–16 / 28–32 ms | 2.8 / 8.6–8.7 / 15 ms |

不绑核时偶尔有单键 40–90 ms（改前改后都有，和是不是第一次载入词库无关）：这台机器有 4 个小核，同一串在小核上慢 1.6 倍，
再赶上被别的进程抢走 CPU 就是这样的尖峰；逐键打字时缺页几乎为零（词库载入时已经全在内存里）。

**词库内存（#233）**。以前一个词条是一个 `LexEntry`（字、音节、声母三份堆分配，结构本身 80 字节），
全拼、简拼、模糊音三张 `HashMap<Vec<_>, Vec<usize>>` 又各存一份键和下标表：雾凇 93 万词常驻约 455 MB，
差不多一个词 490 字节，其中真正的字只有 10 MB。各部分（雾凇 / 万象，MB，按 glibc 的分配粒度估）：

| 改前 | 雾凇 93 万 | 万象 174 万 |
|---|---:|---:|
| 词条结构（`Vec<LexEntry>`，容量按 2 的幂长） | 84 | 168 |
| 每个词的 String / 音节 Vec / 声母 Vec | 30 / 30 / 30 | 56 / 56 / 56 |
| 全拼索引：表 / 键 / 下标表 | 51 / 26 / 39 | 103 / 48 / 72 |
| 简拼索引：表 / 键 / 下标表 | 26 / 9 / 20 | 26 / 10 / 29 |
| 模糊音索引（`prepare_fuzzy` 建）：表 / 键 / 下标表 | 51 / 27 / 37 | 103 / 45 / 66 |
| has_longer 的两张前缀哈希表 | 12 | 12 |
| 载入时把整份快照读进堆（峰值） | 32 | 57 |

现在（`core/src/lexstore.rs`）全部是一列一列的数组：词的字连成一整块、u32 偏移；全拼读音一样的词条共用一组
音节（u16 音节 ID 带儿化位，只存一次），声母由音节现算不再存；三种索引都是「开放寻址的 u32 槽（高 8 位哈希标签，
低 24 位组号）+ 每组一段 u32 下标（CSR）」；has_longer 的前缀集合换成 32 位指纹的开放寻址表（撞了只是少剪枝，
和以前哈希撞了一样不影响结果）。快照文件就是这些数组原样写下来（8 字节对齐），Unix 上 `mmap` 进来直接用，
不再逐条解析、不在堆里复制；别的平台读进一块对齐的内存。

| 改后（快照里各节） | 雾凇 | 万象 |
|---|---:|---:|
| 字 / 字的偏移 / 频次 / 读音组号 | 10.2 / 3.7 / 7.4 / 3.7 | 18.1 / 7.0 / 13.9 / 7.0 |
| 全拼：键偏移 / 键 / 下标偏移 / 下标 / 槽（78.9 万组 / 147.8 万组） | 3.2 / 6.3 / 3.2 / 3.7 / 4.2 | 5.9 / 10.9 / 5.9 / 7.0 / 8.4 |
| 简拼：键偏移 / 键 / 下标偏移 / 下标 / 槽 | 1.2 / 1.5 / 1.2 / 3.7 / 2.1 | 1.3 / 1.5 / 1.3 / 7.0 / 2.1 |
| 两张前缀指纹表 | 6.3 | 9.4 |
| 模糊音：代表组 / 下标偏移 / 下标 / 槽 | 2.9 / 2.9 / 3.7 / 4.2 | 5.3 / 5.3 / 7.0 / 8.4 |
| 合计（就是快照文件的大小） | **75** | **132** |

模糊音索引也写进快照，`prepare_fuzzy` 不用再建（以前雾凇要 0.2–0.3 秒）。快照格式版本从 2 升到 3，旧快照自动重建；
头里有校验和，载入时还逐节检查结构（偏移单调不越界、下标都在范围内、字是合法 UTF-8、哈希表有空槽），
截短、改坏、结构不对都退回读 TSV，查词时不会越界、不会死循环（`damaged_cache_is_rejected`）。
快照只会被「写临时文件再改名」换掉，正在用的映射不受影响；别在输入法开着的时候原地截短它（会 SIGBUS）。

词级语言模型（`words.lm`）也顺手改了：以前整份读进内存再一段一段复制成数组，几十万个词各一个 String，
载入时峰值比常驻多一份文件大小；现在边读边放进最后的数组，词表连成一整块。常驻 57 → 43 MB，载入峰值 94 → 43 MB。

词库加载会自动生成二进制快照（`lexicon.tsv.wcache`）：按「源文件大小 + mtime + 格式版本 + 校验和」
校验，词库更新后自动重建。词库在只读目录（如 `/usr/share`）时快照落到
`$XDG_CACHE_HOME/wowtype/`（默认 `~/.cache/wowtype/`）。快照就是词典本身的数组，载入时映射进来直接用，见上面「词库内存」。

交互预算（<10ms）有很大余量。模糊音索引是**惰性构建**的（模糊音默认关闭）：只从 TSV 建、没有快照时
第一次用到（或者 `prepare_fuzzy`）才建；快照里带着建好的一份。
